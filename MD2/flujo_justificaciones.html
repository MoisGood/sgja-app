1. Flujo general — Ciclo de vida de una solicitud

flowchart TD
    %% Definición de estilos
    classDef prof fill:#dbeafe,stroke:#2563eb,color:#1e40af
    classDef para fill:#d1fae5,stroke:#16a34a,color:#065f46
    classDef insp fill:#ede9fe,stroke:#7c3aed,color:#5b21b6
    classDef est fill:#fef3c7,stroke:#d97706,color:#92400e
    classDef admin fill:#f3f4f6,stroke:#6b7280,color:#374151
    classDef sist fill:#fce7f3,stroke:#ec4899,color:#9d174d
    classDef db fill:#e0e7ff,stroke:#4f46e5,color:#3730a3

    %% Nodos
    START(("Inicio")) --> PROF_CREA["Profesor crea pase\n(GestionPases)"]
    PROF_CREA --> DB_INSERT["📦 solicitudes\nINSERT estado=INJUSTIFICADA"]
    
    DB_INSERT --> PARA_VE["Paradocente ve\nsolicitudes pendientes\n(RegistrarJustificacion / JustificacionesAtrasos)"]
    DB_INSERT --> INSP_VE["Inspector ve\nsolicitudes pendientes\n(VerJustificaciones)"]
    
    PARA_VE --> PARA_DECIDE{"¿Justifica o Rechaza?"}
    PARA_DECIDE -->|Justifica| PARA_JUST["Selecciona motivo\nOpcional: documento"]
    PARA_JUST --> DB_JUST["📦 solicitudes\nUPDATE estado=JUSTIFICADA\n+ motivo + inspector"]
    DB_JUST --> EST_VE["Estudiante ve\nsolicitud justificada\n(MisJustificaciones)"]
    
    PARA_DECIDE -->|Rechaza| DB_RECHAZA["📦 solicitudes\nUPDATE estado=RECHAZADA"]
    DB_RECHAZA --> EST_VE
    
    INSP_VE --> INSP_DECIDE{"¿Justifica o Rechaza?"}
    INSP_DECIDE -->|Justifica| INSP_JUST["Selecciona motivo"]
    INSP_JUST --> DB_JUST
    INSP_DECIDE -->|Rechaza| DB_RECHAZA
    
    PROF_CREA -->|Anula| DB_ANULA["📦 solicitudes\nUPDATE estado=NO_PRESENTADA"]
    DB_ANULA -.->|Solo profesor o admin| PROF_CREA
    
    DB_INSERT --> ADMIN_VE["Admin ve todo\n(acceso completo)"]
    ADMIN_VE --> ADMIN_ANY["Admin puede\njustificar/rechazar\nsobre cualquier solicitud"]

    %% Clases
    class PROF_CREA prof
    class PARA_VE,PARA_DECIDE,PARA_JUST para
    class INSP_VE,INSP_DECIDE,INSP_JUST insp
    class EST_VE est
    class ADMIN_VE,ADMIN_ANY admin
    class DB_INSERT,DB_JUST,DB_RECHAZA,DB_ANULA db
Notas:
• El profesor solo crea pases (no justifica). Su interfaz en móvil es simplificada.
• El paradocente es el rol nuevo que ejecuta la justificación diaria.
• El inspector supervisa y también puede justificar.
• El estudiante solo ve sus solicitudes (no crea, no edita).
• Todas las operaciones van a una única tabla solicitudes con campo estado.

2. Profesor — Versión móvil (crear pase de atraso)

flowchart LR
    INICIO["App → 'Nuevo Pase'"] --> CURSO["Selecciona Curso\n(selector touch)"]
    CURSO --> ESTUD["Selecciona Estudiante\n(lista del curso)"]
    ESTUD --> TIPO["Define Tipo\nATRASO / INASISTENCIA"]
    TIPO --> FECHA["Define Fecha + Hora\n(dentro del día escolar)"]
    FECHA --> CONFIRMA{"¿Confirmar?"}
    CONFIRMA -->|Sí| DB[(solicitudes\nINJUSTIFICADA)]
    CONFIRMA -->|No| CURSO
    DB --> OK["✅ Pase creado\nVuelve al inicio"]
    
    class INICIO,CURSO,ESTUD,TIPO,FECHA,OK prof
    class DB db
Requisitos móvil: Interfaz touch-friendly, paso a paso (stepper), selectores grandes, teclado tipo fecha/hora nativo, sin justificación, sin tabla de historial. Ruta: /gestion-pases/movil.

3. Paradocente — Justificación diaria

flowchart LR
    INICIO["Menú → 'Registrar'\n(o 'Justificaciones de Atrasos')"] --> LISTA["Ve solicitudes\nINJUSTIFICADAS\n(filtra por curso/fecha/tipo)"]
    LISTA --> SEL["Selecciona una\nsolicitud"]
    SEL --> MOTIVO["Elige motivo\ndel catálogo\n(motivos_justificacion)"]
    MOTIVO --> DOC["Opcional:\nDocumento / Certificado"]
    DOC --> OBS["Opcional:\nObservaciones"]
    OBS --> JUSTIFICA{"¿Justificar\no Rechazar?"}
    JUSTIFICA -->|Justificar| DB_J[(solicitudes\nestado=JUSTIFICADA)]
    JUSTIFICA -->|Rechazar| DB_R[(solicitudes\nestado=RECHAZADA)]
    DB_J --> OK["✅ Listo\nSolicitud justificada"]
    DB_R --> OK_R["🚫 Rechazada"]
    
    class INICIO,LISTA,SEL,MOTIVO,DOC,OBS para
    class DB_J,DB_R db
    class OK,OK_R para
Notas:
• El paradocente usa las mismas páginas que el inspector: RegistrarJustificacion, VerJustificaciones, JustificacionesAtrasos.
• Diferencia con inspector: el inspector además tiene dashboard propio.
• El flujo es puramente desktop (no hay versión móvil para paradocente en esta fase).

4. Estudiante — Vista de solo lectura

flowchart LR
    INICIO["App → 'Mis Justificaciones'"] --> CARGA["Carga solicitudes\ndel estudiante autenticado"]
    CARGA --> FILTRO["Filtra por fecha\ntipo o estado"]
    FILTRO --> TABLA["Tabla de solicitudes\n(Solo lectura)"]
    TABLA --> DETALLE["Abre detalle:\nfecha, tipo, estado,\nmotivo, quién justificó"]
    
    class INICIO,CARGA,FILTRO,TABLA,DETALLE est
Requisitos: Ruta /mis-justificaciones. Solo SELECT con WHERE id_estudiante = auth.uid(). Sin botones de crear/editar/eliminar. RLS policy: USING (id_estudiante = auth.uid()).

5. Modelo de datos — Tabla unificada solicitudes

erDiagram
    solicitudes {
        uuid id_solicitud PK
        uuid id_establecimiento FK
        uuid id_estudiante FK
        uuid id_profesor FK
        enum tipo "ATRASO | INASISTENCIA"
        date fecha
        time hora
        enum estado "INJUSTIFICADA | JUSTIFICADA | RECHAZADA | NO_PRESENTADA"
        varchar motivo_codigo "nullable"
        text motivo_descripcion "nullable"
        text observaciones "nullable"
        boolean respaldo_recibido
        varchar tipo_respaldo "nullable"
        uuid id_token_qr "nullable"
        uuid id_inspector_justificador "nullable"
        time hora_justificacion "nullable"
        varchar curso "nullable"
        uuid id_bloque "nullable"
        int bloques_afectados
        timestamptz creado_en
        timestamptz actualizado_en
    }

    estudiantes ||--o{ solicitudes : tiene
    motivos_justificacion ||--o{ solicitudes : "motivo_codigo referencia"
    
    solicitudes }o--|| establecimientos : pertenece
Notas:
• Se unifica en una sola tabla solicitudes (reemplaza a justificadas + injustificadas).
• El campo estado determina en qué etapa está la solicitud.
• id_inspector_justificador registra quién (paradocente/inspector) ejecutó la justificación.
• hora_justificacion registra cuándo se justificó (formato TIME).
• Migración existente: la tabla solicitudes ya está definida en SQL_SUPABASE_CREAR_TABLAS.sql pero no usada por TypeScript.

6. Cambios de permisos vs hoy

👨‍🏫 Profesor

  • ✅ /gestion-pases (desktop) — crear + ver sus pases
  • ✅ /gestion-pases/movil (nuevo) — solo crear pase
  • ❌ /registrar — pierde acceso (ya no justifica)

👷 Paradocente (nuevo)

  • ✅ /registrar — justificar solicitudes
  • ✅ /ver-justificaciones — ver historial
  • ✅ /justificaciones — atrasos e inasistencias

🔍 Inspector

  • ✅ Todo lo que hace paradocente
  • ✅ /gestion-pases (ver todos)
  • ✅ Dashboard inspector

🎒 Estudiante (nuevo)

  • ✅ /mis-justificaciones (nuevo) — solo lectura
  • ❌ No puede crear ni editar
ADMIN: mantiene acceso completo a todo (sin cambios). También mantiene acceso a /secretaria/ausentes (ausencias de funcionarios, que es un módulo aparte).
